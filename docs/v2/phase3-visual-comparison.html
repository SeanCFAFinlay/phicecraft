Phase 3 (GPU coach board) — Task 7 visual parity artifact

All 12 visual.spec.ts scenarios, Canvas2D (visual-shell baseline, desktop-1366 viewport) side by side with WebGL (visual-webgl-shell baseline, same viewport/fixture). These are two deliberately separate, never-cross-diffed baselines — a different rendering pipeline is expected to differ pixel-for-pixel. This page exists so a human can look at the real pixels and decide whether the difference is acceptable before flipping the default renderer.

How this was produced. Each pair below is the actual committed PNG from e2e/__screenshots__/visual-shell/<name>.png and e2e/__screenshots__/visual-webgl-shell/<name>.png (both generated on this machine by the same e2e/visual.spec.ts file, same fixture, same 1366×768 viewport, motion disabled). The delta text under each pair was written after (1) opening both PNGs directly and inspecting them, and (2) a pixel-level diff script (Node + sharp, raw RGBA buffers, per-pixel max-channel delta with a threshold of 12 to ignore anti-aliasing noise) run once per scenario to get an objective differing-pixel percentage, bounding box, and average difference magnitude — quoted in each heading's stats line. The script itself was a scratch file, run and then deleted; it is not part of the committed change.

Board/ice: the outer yellow kick-plate shows a soft radial highlight (a brighter "sheen" patch near the top-left corner) under Canvas2D, rendered via canvas shadow/gradient calls; under WebGL the same ring is flatter and more evenly lit — Pixi's FillGradient approximates but does not reproduce that highlight. tabletop rink diff 3.270% of pixels · avgΔ 66.8 (highest of all 12) · bbox [447,97]–[930,179]

Canvas2D
WebGL

The tabletop (pseudo-3D) rink itself is rendered through the SAME Canvas2D pass-through in both captures — WebGLRenderer's own canvasFallback predicate (tilt > TABLETOP_MIN_TILT) routes tabletop frames to Canvas2D even when ?renderer=webgl is active, by design (Task 5/6). So the ice, boards, sponsor text and all 5 player tokens are pixel-for-pixel the same rendering code path in both screenshots, and the diff tool confirms it: unlike every other scenario, the differing area here is small and tightly bounded rather than smeared across the whole rink. The ENTIRE measured difference is a single DOM overlay — a contextual coaching banner ("Tap Pass with the puck carrier selected to connect a pass.") that is visible in the Canvas2D capture but absent from the WebGL one at the same fixed post-action delay. This is not a rendering-pipeline difference at all (it sits in front of the canvas, not on it); the most likely cause is that the WebGL run's extra async initialization (the dynamic selectRenderer import + two Pixi renderers' own init(), which openFixture already waits on via real paint-activity polling) shifts the wall-clock moment the screenshot is taken relative to whatever shows/expires this banner. Worth a follow-up look if banner timing ever needs to be renderer-independent, but it is a test-timing artifact, not a WebGLRenderer defect.
